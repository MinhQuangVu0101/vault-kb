## Problem Statement

vault-kb exposes the user's Obsidian vault to AI tools as a read-only MCP server. After phases 2.1–2.5 (watcher, bulk edit, semantic search, backlinks/outlinks, local web UI), the next gap is **discovery**: the user can find a note when they remember it exists, but cannot easily discover connections between notes that *should* be linked but aren't yet. This is the highest-friction part of maintaining a connected knowledge base by hand.

## What Makes This Cool

The wedge is **suggested links with LLM-generated reasoning**. Not "here are 5 similar notes" — that's a list. The whoa version is: for each suggestion, a one-line explanation of *why* the notes might belong together, generated locally by the same Ollama instance that already powers embeddings. The user reads "**BERT Paper · 0.81** · Both discuss bidirectional attention mechanisms" and the suggestion is suddenly justified, not just a number.

This is delightful because:
- It turns a passive list into an actionable one.
- It runs 100% locally (no cloud LLM).
- It piggybacks on infrastructure that's already there (Ollama, embeddings, backlinks/outlinks graph).
- It generalizes: once the LLM-reasoning shim exists, future features (cluster naming, search re-ranking) get the same hook for free.

## Constraints

- 100% local; nothing leaves the user's machine.
- Read-only: vault-kb does not write to notes.
- No new heavy dependencies. Ollama is the only AI runtime; we reuse it.
- Must degrade gracefully if Ollama is offline or the chat model isn't installed — fall back to score-only suggestions.
- Web UI runs on `127.0.0.1:7345` (loopback). Internet exposure is Phase 2.7's problem.

## Premises (agreed)

1. **kb_suggest_links is the wedge.** The user identified it as the single feature most likely to produce an Aha-moment in daily use. Cluster-browser, orphan/dead-link cleanup, and pure kb_related are weekly/monthly review features — useful, but not the wedge.
2. **LLM reasoning is the WHOA layer.** Adding a one-sentence "why these belong together" turns a list of cosine scores into an actionable workflow.
3. **Shared infrastructure exists.** Ollama, embeddings, backlinks/outlinks graph, and the local web UI are all in place since phase 2.5. The wedge is a thin layer on top.
4. **The other four graph features are not free.** Each one comes with its own UI surface (treemap, orphan list, etc.) and design decisions (clustering algorithm, naming). Bundling them with the wedge dilutes both.

## Approaches Considered

### Approach A: Wedge 2.6 + Polish 2.7 (chosen)

**Phase 2.6** ships only:
- `kb_suggest_links` MCP tool with LLM-reasoning
- Web UI: a third column ("Connections" panel) showing Backlinks (existing data) and Suggested Links (new, with one-line reason)
- An `embedder.summarize(prompt)` method on the existing embeddings module
- Config: `llmModel` (default uses the same Ollama base; falls back to score-only when unavailable)
- CLI: `--no-llm-summary` flag

**Phase 2.6.1** (later, smaller): `kb_related` MCP tool (similarity-only, no link filter). Shares almost all infrastructure — likely 1-2 hours of work once 2.6 is live.

**Phase 2.7** (later, larger): `kb_clusters`, `kb_orphans`, `kb_dead_links`, full UI treatment (treemap, orphan list, dead-link list, left sidebar navigation), plus tunnel + auth for website embedding.

- **Effort:** ~1–2 days CC time / ~1 week human time
- **Risk:** Low — extends well-trodden infrastructure
- **Reuses:** Ollama embedder, vault index, backlinks/outlinks graph, current web UI shell

### Approach B: Original Maximalist Phase 2.6

All five graph tools (`kb_related`, `kb_suggest_links`, `kb_orphans`, `kb_dead_links`, `kb_clusters`) plus full web UI extension (left sidebar nav, treemap, orphan list, related sidebar). This was the design before the office-hours challenge.

- **Effort:** ~3–5 days CC time / ~3 weeks human time
- **Risk:** Medium — five new tools, clustering algorithm, three new UI views, k-means implementation
- **Why rejected:** office-hours forcing question revealed only one of the five features is the daily-Aha. Bundling them ships less polished versions of all five and delays the wedge by weeks.

### Approach C: Pure Minimum (kb_suggest_links only, no UI, no LLM)

Just the MCP tool, score-only output, no UI changes. Smallest possible diff.

- **Effort:** ~4–6 hours CC time
- **Risk:** Very Low
- **Why rejected:** strips out the WHOA layer (LLM reasoning) and the UI surface, both of which the user explicitly chose. The wedge without its magic is no longer a wedge — it's just another search.

## Recommended Approach

**Approach A.** Captures the wedge, adds the WHOA, leaves the rest cleanly deferred to 2.6.1 and 2.7. Each subsequent phase is small because the shared infrastructure (LLM-reasoning hook, "Connections" panel) is already in place after 2.6.

## Implementation Notes

### New files
- `src/suggest-links.js` — exports `suggestLinks({ vaultIndex, embedder, path, limit, minScore })`. Computes embedding similarity to the source note, filters out already-linked targets (both outlinks and backlinks), optionally calls `embedder.summarize()` for the reason, returns ranked results.
- `test/suggest-links.test.js` — unit tests with a stub embedder.

### Changed files
- `src/embeddings.js` — add `async summarize(prompt)` method that calls Ollama `/api/generate` with the configured `llmModel`. Return null on failure (caller handles fallback).
- `src/index.js` — register `kb_suggest_links` MCP tool; format output as numbered list with `title · path · score · reason` per entry.
- `src/web.js` — new endpoint `GET /api/suggest-links?path=…&limit=…`; returns JSON `{ rows: [{ path, title, score, reason }] }`.
- `src/config.js` — add `llmModel` (string, optional; default `"llama3.2:3b"`). Gemma 3 4B (`"gemma3:4b"`) is the documented upgrade path for users who want better explanation quality and have the RAM. Setup docs add a `ollama pull llama3.2:3b` step alongside the existing `nomic-embed-text` pull.
- `public/index.html` — add third column "Connections" to the `<main>` grid; two sections inside: `<section id="backlinks">` and `<section id="suggest-links">`.
- `public/app.js` — on note-detail open, fetch `/api/suggest-links`, render the panel; backlinks come from the existing `/api/read` response.
- `public/style.css` — adjust grid to three columns; collapse the third on narrow screens (responsive breakpoint).

### Out of scope (Phase 2.6.1 or 2.7)
- `kb_related`, `kb_clusters`, `kb_orphans`, `kb_dead_links` MCP tools.
- Treemap cluster browser, orphan list view, dead-link list view, left-sidebar navigation.
- Cluster naming, k-means implementation.
- Tunnel/Cloudflare integration, auth layer, website embedding.
- Any write tools (creating links, editing notes).

## Open Questions

1. **Caching reasons.** Should generated reasons be cached on disk (keyed by source-path + target-path + content hashes)? Skipping cache keeps the implementation simple but means every web UI open re-generates reasons. Recommendation: no cache in 2.6; revisit if it feels slow.
2. **Backlink filter.** When filtering "already linked" notes from suggestions, do we filter only outlinks (from source) or also backlinks (to source)? Recommendation: filter both — if a note already links to or from this one, it's not a missing connection.

## Decided

- **Default chat model:** `llama3.2:3b`. Small enough to run fast on Apple Silicon (~2GB), strong instruction-following for short outputs. `gemma3:4b` documented as the upgrade for users who want higher explanation quality. `kb_stats` exposes `llmModel` so the user can see what's actually running.

## Success Criteria

- `kb_suggest_links --path X` returns at least one well-reasoned suggestion for a typical mid-sized note in the vault.
- The "Connections" panel in the web UI renders backlinks immediately and suggested links within ~3 seconds on a vault of 200+ notes.
- With Ollama offline, the tool still returns score-only suggestions (no crash, clear "LLM unavailable" indicator in output).
- Unit tests cover: source-note resolution, link-graph filtering, score thresholding, summarize-fallback path.
- Manual smoke test: open a note in the web UI, see at least one suggestion with a sentence-long reason that visibly relates the two notes.

## Distribution Plan

Existing pipeline covers this. vault-kb is a Node.js MCP server in a Git repo; users `git pull && npm install`. No new packages, no separate deployable artifact, no CI changes beyond running tests.

## What I noticed about how you think

- **You default to maximalist scope.** Twice you picked the "all of the above" option — all four graph features, then Option C (everything + UI). When forced to pick one, you picked the genuinely highest-value one. The instinct to bundle is strong; the instinct to prioritize is sharper.
- **You care about visual feel before utility.** You picked the treemap over a list for clusters, the right sidebar over the bottom panel for related notes. Atlas-feeling matters to you. That taste shows up in the product.
- **You invoked /office-hours mid-flow.** That's unusual — most users let a brainstorming session run its course. Calling for a second lens before committing means you trust the design process enough to stress-test it. That instinct is rare.
- **"Nur für mich erstmal."** The "erstmal" (for now) does work. You're building for yourself today but you're not closing the door on others later. That framing keeps the design honest: solve your own problem first, decide later whether to scale.

## The Assignment

After Phase 2.6 lands and you've used `kb_suggest_links` on real notes for a week, **write down three suggestions you actually acted on and three you ignored**. The pattern in those six examples will tell you more about whether the LLM-reasoning is pulling its weight than any score metric can. That feedback is what should drive Phase 2.7's design.
