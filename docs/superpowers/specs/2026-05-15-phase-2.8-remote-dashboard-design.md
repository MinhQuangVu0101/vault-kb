## Problem Statement

vault-kb's local web UI (`127.0.0.1:7345`) is only reachable from the user's Mac. The user wants to use the dashboard from anywhere — laptop on the road, phone, iPad — without exposing the vault to the public internet. Authentication and tunneling shouldn't require writing custom auth code or running a public server with the vault on it.

Secondarily: the current UI assumes desktop width. On a phone (375–500px), the existing 2-column layout (results + detail) is cramped, and the Connections sidebar already hides under 1100px (Phase 2.6).

## What Makes This Useful

Cloudflare Tunnel + Cloudflare Access is the "boring, polished" solution to this exact problem: the user installs `cloudflared` on their Mac, configures a tunnel from a subdomain to `localhost:7345`, and Cloudflare Access gates the subdomain with email-OTP login restricted to a single Gmail address. No code in vault-kb handles auth; no public server holds the vault; the user gets `vault.deine-domain.com` from any device after a magic-link login.

vault-kb's only code additions are cosmetic: a public-URL log line, a small "logged in as" badge in the UI header (reading Cloudflare's identity header), and a mobile-responsive layout that shows one pane at a time on phones with a back button to return to the results list.

## Constraints

- 100% local. The vault never leaves the user's Mac. Cloudflare Tunnel proxies bytes; it doesn't store them.
- Read-only continues. Phase 2.8 doesn't change any tool to write to the vault.
- No new npm dependencies. All tunneling is external (`cloudflared`).
- The MCP stdio mode (Claude Desktop / Claude Code integration) stays unchanged — local-only.
- Web server still binds to `127.0.0.1:7345`. Cloudflare Tunnel is the only way external traffic reaches it.

## Premises (agreed)

1. **Cloudflare does auth.** vault-kb trusts that Cloudflare Access has been configured correctly. No JWT verification in vault-kb itself (deferred — see "What's out of scope").
2. **Email-OTP for a single Gmail.** Cloudflare Access "One-time PIN" login method, policy allow-list with the user's Gmail address only. No OAuth dance, no passwords, just an email code.
3. **Tunnel runs as a launchd service.** Manual `cloudflared tunnel run` works for testing; the production setup uses `cloudflared service install` so the tunnel survives reboots and is available whenever the Mac is on.
4. **Phone is for reading, desktop is for connecting.** Mobile shows one pane at a time (results OR detail). Connections sidebar stays hidden under 1100px as Phase 2.6 already specified — Suggested-Links exploration is a desktop workflow.

## Approaches Considered

### Approach A — Config + Minimal Helpers (chosen)

- README "Remote access (optional)" section with step-by-step Cloudflare Tunnel + Access setup
- `VAULT_KB_PUBLIC_URL` env var → logged on boot alongside the local URL
- `/api/identity` endpoint reads `Cf-Access-Authenticated-User-Email` from the request, returns `{ email }` or `{ email: null }`
- UI auth badge in header (renders `📧 email · logout` when identity present, hidden when local)
- Mobile responsive layout (<600px): one pane at a time, back-arrow button in detail view
- Logout link points to Cloudflare's standard `/cdn-cgi/access/logout`

**Effort:** ~5–7 hours CC time
**Risk:** Low — vault-kb stays code-light, Cloudflare handles auth + identity + transport
**Reuses:** existing web UI, existing JS `activePath` state for the body-class toggle

### Approach B — A + JWT verification in vault-kb

Same as A, plus vault-kb itself verifies the `Cf-Access-Jwt-Assertion` header against Cloudflare's public keys for every `/api/*` request. Defense-in-depth: if the Access policy is ever misconfigured to be public, vault-kb still rejects unauthenticated requests.

- **Effort:** ~1–2 days
- **Why rejected:** crypto code (JWT verification + JWKS rotation) is security-critical and easy to get subtly wrong. For a solo user who configures Access themselves and tests the email-only policy works (i.e., logging out and confirming the magic-link gate appears), the marginal value of double-checking JWTs is low. Revisit if the use case ever grows beyond single-user.

### Approach C — Full sysadmin treatment

Everything in B, plus an installer script for `cloudflared` as a launchd service, an interactive setup wizard, a `/healthz` endpoint for tunnel monitoring, and per-request access logs.

- **Effort:** ~3–4 days
- **Why rejected:** maximalism. The setup-wizard surface and the launchd installer save maybe 20 minutes of one-time setup, at the cost of days of code and ongoing maintenance for OS-specific install logic. Manual `cloudflared service install` from the README is fine.

## Recommended Approach

**Approach A.** Captures the wedge ("reachable from anywhere, with login") with minimal vault-kb code surface. Cloudflare carries the operational weight. Everything in A is reversible — if the user wants to switch to a different tunnel (Tailscale Funnel, etc.) later, only the README section needs updating.

Modify `openNote(path)` to add a `note-open` class to `document.body` when a path is set. Add a back-button click handler that clears `activePath` and removes the class. Mobile breakpoint `@media (max-width: 600px)`: hides `#results` when body has `.note-open` class, hides `#detail`'s back-arrow when body does NOT have the class, makes `#detail` full-width when `.note-open` is present, hides `#detail` when not. Connections sidebar stays hidden via Phase 2.6's existing 1100px breakpoint.

### Out of scope (deferred or later)
- JWT verification of Cloudflare Access tokens in vault-kb (Approach B).
- Service Token / machine-to-machine auth (for headless clients).
- Tunnel auto-installer (Approach C).
- Slide-in or bottom-drawer Connections panel on mobile — Phase 2.8.1 if it turns out to be needed.
- CORS configuration — the dashboard is same-origin via the tunnel; no cross-origin requests in scope.
- Auth for the MCP stdio mode — stays local-only.

## Decided (during brainstorming)

- **Logout link:** included. Comfort feature, four lines of code, points to Cloudflare's `/cdn-cgi/access/logout`.
- **Login method:** Cloudflare Access "One-time PIN" (email-OTP) restricted to a single Gmail address via a Cloudflare Access policy.
- **Mobile Connections sidebar:** stays hidden under 1100px (Phase 2.6 default). Phone is a reading device; if the user finds they miss Suggested Links on mobile, that becomes its own small phase.

## Open Questions

1. **Cf-Access-Email header trust on localhost:** If the user opens `http://127.0.0.1:7345` directly and manually sets the `Cf-Access-Authenticated-User-Email` header (e.g., via a browser extension), the badge would display that email without any actual authentication. The dashboard is local-only when accessed via loopback, so the only attacker model is the user themselves — but it's worth documenting that the badge is informational and not a security boundary. Recommendation: note this in the spec; revisit only if a multi-user scenario emerges (which would require Approach B).
2. **Session timeout default:** Cloudflare Access defaults to 24-hour session lifetime. If the user wants shorter (e.g., 1h for paranoid mode), it's a Cloudflare-side config — document the relevant Cloudflare setting in the README so the user can adjust.

## Success Criteria

- After completing the README setup steps, `https://vault.<user-domain>` returns the vault-kb web UI after a one-time email-OTP login.
- Boot log shows the public URL when `VAULT_KB_PUBLIC_URL` is set; falls back to local URL only when unset. Local startup behavior is unchanged.
- Auth badge appears in the UI header with the authenticated email and a working logout link only when accessed via the tunnel. Direct `127.0.0.1:7345` access shows no badge (clean local browsing).
- On a phone (≤600px), tapping a search result shows the note detail full-width; tapping the back-arrow returns to the results list. iPad portrait (~768px) and larger keep the side-by-side results + detail layout. The Connections sidebar is not visible on phone (intentional).
- `/api/identity` returns `{ email: null }` for local access and `{ email: "..." }` for Cloudflare Access-authenticated requests.
- All tests pass; one new unit test for `/api/identity` (with and without the email header).

## Distribution Plan

Existing pipeline covers this. The vault-kb side is documentation + small UI tweaks; the Cloudflare side is user-side configuration. No new packages, no new deployable artifacts. The user runs `git pull && npm install` after merge (no new deps but standard practice) and follows the README steps once for tunnel setup.
