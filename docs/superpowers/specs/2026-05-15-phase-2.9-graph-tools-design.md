# Design: Phase 2.9 — Graph Tools (kb_related + kb_orphans + kb_dead_links) with Left-Nav UI

Status: DRAFT

## Problem Statement

vault-kb's web UI is shaped around per-note search and reading. Phase 2.6 added Suggested Links (per-note discovery for missing connections). Three deferred features from Phase 2.6 remain:

- **kb_related** — per-note "what's similar to this?" without the not-yet-linked filter. Closer to passive discovery than the active linking workflow of kb_suggest_links.
- **kb_orphans** — vault-wide cleanup: notes with no incoming and no outgoing resolved links.
- **kb_dead_links** — vault-wide cleanup: every `[[Reference]]` in the vault that doesn't resolve to a real note.

Today these queries can only be done by hand. The user wants:
1. AI-callable MCP tools for all three (so AI agents can do orphan/dead-link cleanup passes on demand).
2. A UI surface for the cleanup workflows so the user can sit down once a month and work through the lists.

Out of scope (deferred again): kb_clusters and a Treemap UI — requires a clustering algorithm and a new UI surface that does not slot into the existing patterns.

## What Makes This Useful

The cleanup tools become **workflows**, not just queries. A user opens the "Dead Links" view, sees a list of broken `[[refs]]` grouped by source note, clicks one → the detail pane opens the source note with the broken link visible in context, the user fixes it in Obsidian, the next refresh removes it from the list. Same for orphans: click an orphan → detail pane shows the note → the user can decide to delete it, link it from somewhere, or accept that it's intentionally standalone.

kb_related complements kb_suggest_links: where kb_suggest_links nudges the user to *create* a connection, kb_related surfaces existing similarity for *passive* discovery while reading.

## Constraints

- 100% local. All graph computation happens on the user's machine over the existing SQLite store.
- No new npm dependencies. Reuse `links.js` (parseLinks + buildResolver) and `vault-index.js` (findRelatedByPath).
- The MCP stdio mode keeps the same surface — three new tools added, no existing tools changed.
- The local web UI is the only UI affected. The Cloudflare Tunnel + Access setup from Phase 2.8 carries over (the new views are accessible remotely the same way the existing UI is).

## Premises (agreed)

1. **kb_related is the daily-Aha.** Even within the three deferred tools, kb_related has the highest per-session usage frequency (every note opened could benefit). kb_orphans and kb_dead_links are monthly hygiene tasks.
2. **Cleanup tools deserve UI.** AI-callable MCP output is useful, but the user wants to actually sit and work through cleanup lists themselves. UI is not over-engineering — it's the actual workflow.
3. **Left-nav layout, not mode-dropdown.** The user picked the Phase 2.6 Mockup B layout (left navigation strip) over the mode-dropdown extension. This is a meaningful UI restructure but matches the original Phase 2.6 vision.
4. **Click on cleanup-list entry stays in mode.** When the user clicks an orphan or dead-link entry, the detail pane opens the note BUT the nav stays on the active mode. The list remains visible alongside the detail — natural "work through the list" cadence.

## Approaches Considered

### Approach A — Three MCP tools + Left-Nav UI (chosen)

**MCP layer:**
- `kb_related(path, limit, minScore)` — top-N similar notes regardless of link status. Wrapper around existing `findRelatedByPath` with `excludePaths: []`.
- `kb_orphans(limit)` — list of notes with no incoming AND no outgoing resolved links.
- `kb_dead_links(limit)` — list of `{ sourcePath, raw }` pairs for every unresolved `[[ref]]` in the vault.

**Web layer:**
- New endpoints: `GET /api/related?path=...&limit=...`, `GET /api/orphans?limit=...`, `GET /api/dead-links?limit=...`.

**UI layer:**
- New left-nav strip (~64px wide on desktop): three items — `Search`, `Orphans`, `Dead Links`. Default active: Search.
- When `Orphans` is active: search input + filter row hidden. `#results` shows orphan list (same hit-card style as search results). Click → detail pane opens the note; nav stays on `Orphans`.
- When `Dead Links` is active: `#results` shows two-line entries — source-note title + the broken `[[ref]]` string. Click on the source title → detail pane opens that note. Nav stays on `Dead Links`.
- Connections sidebar visibility unchanged (still hides under 1100px). It shows whatever note is currently open in `#detail` — applies in all three views (Search / Orphans / Dead Links) once the user clicks an entry.
- Related-Notes section added inside Connections sidebar between Backlinks and Suggested Links. Visible for any opened note, regardless of which view sourced it.

**Mobile (≤600px):**
- Left-nav becomes a horizontal tab bar between header and content (three small pills).
- Existing `.note-open` one-pane behavior unchanged.

**Effort:** ~8–10h CC time
**Risk:** Medium — UI restructure touches `index.html`, `style.css`, `app.js` substantially; new state machine for active-nav.
**Reuses:** `findRelatedByPath` (Phase 2.6), `links.js`, the existing `#results`/`#detail` rendering code, identity badge + boot log + mobile responsive from Phase 2.8.

### Approach B — Three MCP tools + Mode-Dropdown UI

Same MCP and Web layer as A. UI adds two values (`orphans`, `dead-links`) to the existing mode-select dropdown. Search button label changes to "List" when in those modes. No left-nav, no layout restructure.

- **Effort:** ~6–7h
- **Why rejected:** the user explicitly preferred Approach A's left-nav layout. The mode-dropdown is technically cleaner (less UI change) but the user wants the more substantial UI surface. Their call.

### Approach C — Three MCP tools, no UI

Same MCP and Web layer. No UI changes. Cleanup happens via AI-mediated workflow (user asks AI "find my orphans").

- **Effort:** ~3–4h
- **Why rejected:** the user picked "Cleanup-Tools auch mit UI" — wants to sit down and do cleanup directly without AI mediation.

## Recommended Approach

**Approach A.** Captures the user's preference for a left-nav layout while keeping the cleanup workflow first-class. The left-nav restructure is real work but pays off in clarity: each mode has its own logical surface instead of overloading the search input.

## Implementation Notes

### New files
- `src/related.js` — thin wrapper exporting `relatedNotes({ vaultIndex, path, limit, minScore })`. ~15 lines. Mirrors the suggest-links.js shape for consistency.
- `test/related.test.js` — 2–3 unit tests (stub vaultIndex, verify findRelatedByPath delegation + filter/sort).
- `test/vault-index-orphans.test.js` — 2 tests for `findOrphans` (tmp vault with linked + unlinked notes).
- `test/vault-index-dead-links.test.js` — 2 tests for `findDeadLinks` (tmp vault with one note pointing to a missing target).

### Changed files
- `src/vault-index.js` — add `findOrphans({ limit })` and `findDeadLinks({ limit })` methods. Both walk the existing `notes` table and use `parseLinks` + `buildResolver` from `links.js`. Return rows with the same shape as `search()` for orphans, and `{ sourcePath, title, raw }` shape for dead-links.
- `src/index.js` — register three new MCP tools: `kb_related`, `kb_orphans`, `kb_dead_links`. Each handler delegates to the corresponding `vaultIndex.*` method (or `related.js` wrapper) and formats the output as text (orphans = numbered list like kb_search; dead-links = grouped by source).
- `src/web.js` — three new endpoint cases: `/api/related`, `/api/orphans`, `/api/dead-links`. Input-validation matches `/api/suggest-links` style (limit must be a positive integer; out-of-range returns 400). Limits differ by tool: `/api/related` caps at 20 (UI shows 5; per-note exploration); `/api/orphans` and `/api/dead-links` cap at 200 (vault-wide lists).
- `public/index.html` — major restructure:
  - Wrap header content unchanged.
  - Restructure `<main>` to include a new `<nav id="view-nav">` as the first grid column, with three items.
  - The existing `<section class="search">` becomes a child of a new `<section id="view-search">` wrapper that only displays when nav is on `Search`.
  - Two new wrappers: `<section id="view-orphans">` and `<section id="view-dead-links">`, each containing the appropriate `#results`-style list area.
  - Detail pane and Connections sidebar remain inside the main grid, shared across all modes.
- `public/app.js`:
  - New `activeView` module variable (default `"search"`).
  - New `switchView(name)` function that toggles a class on `<body>` (e.g. `view-search`, `view-orphans`, `view-dead-links`) and triggers the corresponding loader.
  - `loadOrphans()` and `loadDeadLinks()` async functions that fetch the new endpoints and render into shared `#results`.
  - `loadRelated(path)` analogous to `loadSuggestions(path)`, renders into a new "Related" section in the Connections sidebar.
  - `openNote(p)` unchanged — works regardless of active view.
  - `doSearch()` only runs when `activeView === "search"`.
- `public/style.css`:
  - Add `#view-nav` with vertical flex layout on desktop, ~64px wide.
  - Grid template updated: `#view-nav | content | #connections` on wide screens; collapse to top-tab strip on `≤600px`.
  - Body-class based view-switching: `body.view-search #view-orphans { display: none }`, etc.
  - Mobile: nav becomes horizontal tab bar between header and content.
- `README.md` — three new MCP tools documented in the tools list. Brief mention of the cleanup-list UI in the Setup section (optional).

### Out of scope (deferred or later)
- `kb_clusters` MCP tool + Treemap UI — its own future phase.
- Auto-fix suggestions for dead links — manual cleanup in Obsidian for now.
- Orphan/dead-link counts in `kb_stats` — could be added later if useful.
- A dedicated "Stats" view in the nav — current header stats-bar covers it.
- Recompute/refresh button on the cleanup lists — the lists refresh when the user navigates to them anyway.

## Open Questions

1. **Orphan definition: strict vs lenient.** Strict = no incoming AND no outgoing resolved links. Lenient = no incoming OR no outgoing (one-way is also orphan-ish). Recommendation: strict definition. A note with only outgoing links is a "leaf reading note" (e.g., a daily journal entry that references topic notes) — not orphan-ish. A note with only incoming links is a "hub leaf" (referenced but doesn't reference back) — also intentional. Strict catches the genuinely isolated notes. Caller can compose other queries if they want lenient.
2. **Dead-link grouping: by source or by target.** By source is more useful for cleanup (fix all bad refs in one note in one sitting). Recommendation: group by source note, sort by source-path ascending.
3. **Limit behavior:** what's the default? Recommendation: `limit=50` for both orphans and dead-links (most vaults won't have hundreds of either; if they do, that's its own signal). Max 200.

## Success Criteria

- `kb_related` MCP tool returns top-N similar notes for a typical indexed note when called via Claude Desktop or Claude Code, with score values and no link filtering.
- `kb_orphans` returns notes with no incoming and no outgoing resolved links. Output is a numbered list with title + path.
- `kb_dead_links` returns broken `[[refs]]` grouped by source note. Output identifies the source title and the unresolved string.
- All three are accessible via `/api/*` from the local web UI.
- The left-nav shows three items: Search (default), Orphans, Dead Links. Clicking switches the visible view without a page reload.
- Clicking an entry in Orphans or Dead Links opens the relevant note in the detail pane while keeping the nav on the active view.
- On mobile (≤600px), the nav collapses to a horizontal tab bar at the top of the content area; the existing one-pane-at-a-time flow for results/detail remains.
- The Connections sidebar gets a new "Related (N)" section between Backlinks and Suggested Links (visible only in Search mode when a note is open and screen ≥1100px).
- All existing tests pass; at least 6 new unit tests across related/orphans/dead-links modules + web endpoints.
